# Free database options for the catalog

Verified 2026-11-08 by a survey workflow (6 researchers) plus one adversarial verifier per shortlisted option, using official pricing and docs pages. Free tiers change often: re-check before acting.

Workload assumed: ~145k rows now, 250–400k within a year, ~1.4 KB metadata + one 384-d gte-small vector per row, hybrid keyword + vector search, server-side access only.

Decision 2026-11-08: stay on Supabase free and trim (see migrations 20261108000004–06). Best durable free Postgres alternative found: Prisma Postgres Free (2 GB), pending a pgvector version check.

### Prisma Postgres (Free)

- **Vector:** pgvector ('vector' extension listed as supported). halfvec/HNSW not confirmed on Prisma's own pages (pgvector >=0.7 has both); verify with SELECT extversion.
- **Keyword search:** Native Postgres tsvector/GIN; also lists pg_search (BM25) and pg_trgm, unaccent.
- **Pause / expiry:** 'Free forever', 'no time limit'. No inactivity pause stated on pricing/FAQ pages. Exceeding the ops quota blocks reads and writes until month reset (data not deleted).
- **Verifier corrections:**
  - The 2 GB is per workspace and shared by all 50 databases, not 2 GB for each database. Source: prisma.io/postgres/free-postgresql-hosting, 'shared across up to 50 databases'.
  - Connections: the Free plan allows 10 pooled and 10 direct per database, but 5 of the direct ones are reserved for the platform, so about 5 are usable. The pooled connection runs PgBouncer in transaction mode with a 10-minute query timeout. SET, prepared statements and temp tables are lost at each transaction boundary. hybrid_search already uses set_config(..., true), which is transaction-local, so it works through the pooler. Vercel functions should use the pooled string.
  - Quota exhaustion: the claim is confirmed (queries blocked, data not deleted, reset on the 1st of the month). One addition: a 24-hour grace restore is available once per workspace and never renews.
  - The free ops quota changed recently. Older Prisma pages and a 2025 Vercel thread cite 100k ops/month; today's pricing page says 200k.
  - Inactivity: the claim says nothing is stated, but Prisma does state that idle Free databases scale to zero and wake on the next query, and that claimed or Console-created databases have no time limit. Only unclaimed instant databases (create-db) are deleted after 24h. Counter-evidence: in a Vercel community thread from Oct 2025, a Free Prisma Postgres database was shown as 'Suspended' at 47.1k of 100k ops. The thread has no official explanation and was never resolved, so it is anecdotal but unexplained.
  - pgvector version is unverified, and the risk is larger than halfvec/HNSW. Our hybrid_search (migrations 20261108000003 and 000004) runs set_config('hnsw.iterative_scan','relaxed_order'), which needs pgvector >= 0.8.0. Supabase runs 0.8.2. Prisma's extensions page lists 'vector' with no version.
  - Every credential has full access to its database. Read-only or per-schema credentials are impossible, not just CREATE ROLE. With RLS policies that name anon/authenticated dropped, isolation rests entirely on keeping the connection string server-side.
  - Operation counting: the FAQ says every interaction counts, SELECT 1 included, regardless of how long it runs. So driver handshake or introspection queries and explicit BEGIN/COMMIT probably count too (inferred). Still far below 200k at our volume as long as the crawler upserts in multi-row batches.
  - Measured storage today: Supabase reports 472 MB total for 144,298 rows, with only 56,896 embedded. The capability table plus its indexes is 421 MB, and the HNSW index is 63 MB for 57k vectors. Fully embedded at 145k rows comes to about 635 MB, roughly 4.4 KB per row with all indexes. At 250k rows that is about 1.1 GB; at 400k rows about 1.75 GB, which is 88% of 2 GB before upsert bloat or an extra pg_search BM25 index. Some relief: Supabase's 472 MB includes auth/storage schemas that would not move. Whether indexes count toward the cap is still not documented, so assume they do.
  - Not relevant to us: Prisma Accelerate's cache is retiring on December 1, 2026.
- **Blockers:**
  - pgvector version is unverified. hybrid_search needs >= 0.8.0 for hnsw.iterative_scan and >= 0.7 for halfvec. Before committing, check on a free DB with SELECT extversion FROM pg_extension WHERE extname='vector'.
  - Headroom at 400k rows is thin (about 1.75 GB of 2 GB, shared across the workspace). If growth runs past about 450k rows, or a pg_search BM25 index is added, the cap is hit with no paid overage on Free. Mitigation: drop the trgm index or slim the jsonb columns (the uncommitted slim_catalog migration).
  - There is a hard stop at 200k ops/month. That is fine at a few hundred queries a day, but a runaway crawler loop or row-by-row writes could exhaust it, and the 24h grace works only once per workspace.
  - A Free DB was reported 'Suspended' in Oct 2025 below its quota, and the cause is unexplained. There are no backups on Free, so a scheduled pg_dump from GitHub Actions is mandatory.
- **Migration:** Medium. (1) Migrations: drop the 'extensions.' schema prefix on halfvec/halfvec_ip_ops, or create an extensions schema; remove the 'revoke ... from anon, authenticated' lines and any role-named RLS policies. (2) Code: the crawler calls PostgREST through supabase-js (db.rpc in crawler/db.ts:17,45 and crawler/embed.ts:66-67). These become node-postgres calls, e.g. SELECT upsert_capabilities($1,$2,$3), against the pooled URL; catalog_db_bytes still works. src/ has no Supabase usage yet. (3) Query-time embeddings currently come from the Supabase Edge Function 'embed' (crawler/embed.ts:32). Either keep the Supabase project alive only for that function (it pauses after 7 idle days) or move gte-small (Transformers.js) into a Vercel function. (4) Data move: pg_dump/pg_restore --no-owner --no-privileges. (5) Add a scheduled pg_dump backup.

### Turso (libSQL Cloud) Free

- **Vector:** Native column types F64/F32/F16/FB16/F8/F1BIT_BLOB, up to 65536 dims. Cosine (default) or L2. DiskANN ANN index via libsql_vector_idx and vector_top_k(). F16 at 384-d = 768 B/row. Index needs a rowid or single-column PK.
- **Keyword search:** FTS5 is preloaded on Turso Cloud ('Full-text search and indexing'). The new Tantivy-based FTS (USING fts, fts_match/fts_score) is part of the new Turso engine and is experimental (blog, 2026-01-27). Do not rely on it for Cloud.
- **Pause / expiry:** Not a trial. Turso CLI docs say free-plan databases are archived after 10 days of inactivity and restored with 'turso group unarchive' (search snippet; the page did not load). Older docs mention scale-to-zero after 1 h idle. A daily crawler keeps it active.
- **Verifier corrections:**
  - MAIN ERROR, the storage math: the claim says 5 GB 'easily' holds 400k rows plus the DiskANN index. That is false with default index settings. The official docs say the index uses about N x (Storage(T1) + M x Storage(T2)) bytes, with max_neighbors M = 3*sqrt(D) and compress_neighbors = 'no compression' (neighbors stored in the column type). At 384-d F16 that is M ~ 59, so 768 + 59 x 768 ~ 46 KB per row. That comes to ~6.7 GB at today's 145k rows and ~18 GB at 400k, so the index alone breaks the 5 GB limit now.
  - Fitting in 5 GB needs index tuning. With compress_neighbors=float1bit, ~768 + 59 x 48 B ~ 3.6 KB/row, which is ~0.5 GB at 145k and ~1.45 GB at 400k. Add the base table (~2.2 KB/row, ~0.87 GB at 400k) and FTS5, and the total is roughly 2.5-3 GB at 400k, which fits. Alternatively use float8 with max_neighbors ~20 (~8.4 KB/row, ~3.4 GB index at 400k, which is tight). Turso's own space-complexity blog says lower neighbors and compression trade off accuracy, and it has no recall data at 100k+ scale.
  - Storage counting is now officially stated, not just 'likely'. The usage doc measures storage with dbstat over 'all tables and indexes' in 4 KB pages. So vector and FTS5 indexes count.
  - Hidden limit not mentioned in the claim: VACUUM is disabled on Turso, so storage cannot be compacted. Pages freed by daily upsert churn and index rebuilds stay allocated. SQLite reuses free pages, but the file never shrinks.
  - Archiving is now verified by fetching the page directly (not a snippet). The CLI doc says 'Databases get archived after 10 days of inactivity for users on a free plan', and they are restored with 'turso group unarchive'. The daily crawler should keep the database active, but a crawler outage longer than 10 days archives it and the app goes down until someone unarchives it manually.
  - Row counting risks the claim did not cover. Reads count every scanned row, including joins and subqueries, and each row an update modifies. Adding an index costs one read per existing row. The docs do not say whether DiskANN shadow-index rows or FTS5 shadow tables (not sqlite_-prefixed, so probably counted) count as reads or writes. If each DiskANN insert counts the neighbor rows it updates (~59), the initial 145k load could use ~8.7M of the 10M monthly write quota. On Starter/Scaler, going over a limit returns a BLOCKED error; the free-plan behavior is not documented.
  - Supabase acquisition: the claim says no commitment to the free plan was found. In fact the Supabase blog says 'For existing users, nothing changes' and that Turso 'will continue operating'. It still says nothing about the free plan or pricing specifically.
  - Engine transition risk: DiskANN/libsql_vector_idx is documented for libSQL. Turso is rewriting its engine (new Turso Cloud beta banners on its site), and I found no official statement that the DiskANN index carries over to the new engine. This is unverified, not a confirmed deprecation.
  - Post-filter is confirmed. The docs show vector_top_k returning ROWID/PK and being joined back to the table, with WHERE applied in the outer query, plus partial indexes as the only pre-filter. So metadata-filtered ANN can return fewer than k rows.
  - Fit should be downgraded from 'strong' to 'moderate'. It is feasible only with non-default index settings and a full rewrite away from Postgres.
- **Blockers:**
  - The DiskANN index with default settings (F16 neighbors, max_neighbors~59) takes ~46 KB/row, about 6.7 GB at 145k rows, so it breaks 5 GB today. You must set compress_neighbors=float1bit (or float8 plus a low max_neighbors) and accept some recall loss, which is unmeasured at this scale.
  - Not Postgres. All migrations, the plpgsql hybrid_search RPC, jsonb/text[] columns, halfvec and RLS have to be rewritten. Hybrid RRF across vector_top_k and FTS5 bm25 is not documented and would have to be built and tested by hand.
  - Free databases are archived after 10 days of inactivity and need a manual unarchive.
  - It is unclear whether DiskANN neighbor-row updates and FTS5 shadow-table reads count against the 10M writes and 500M reads per month. The initial bulk load could get close to the write cap.
  - Ownership and engine transition (Supabase acquisition announced 2026-10-02; new Turso engine). There is no explicit commitment to keep the free-plan terms, and no confirmation that the DiskANN index carries over to the new engine.
- **Migration:** High, roughly a 2-4 day rewrite. Schema: jsonb becomes JSON text, text[] becomes a JSON array or a join table, halfvec(384) becomes F16_BLOB(384) via vector16(), and the vector index needs a tuned libsql_vector_idx with compress_neighbors/max_neighbors. Add an FTS5 virtual table plus sync triggers or an external-content table. Rewrite hybrid_search from a plpgsql RPC into one SQL statement (CTEs over vector_top_k and FTS5 MATCH/bm25, RRF in SQL) called from app code. Port crawler/db.ts upserts to @libsql/client or @tursodatabase/serverless (the docs recommend the latter for serverless). RLS goes away and is replaced by a server-only auth token; that fits, since access is server-side only. Re-embedding is not needed: the existing gte-small vectors can be exported and reused.

### Qdrant Cloud free cluster

- **Vector:** Dense float vectors with HNSW, plus sparse vectors. 400k x 384 float32 is about 614 MB raw, which is tight in 1 GB RAM, so use a float16/uint8 datatype or on-disk vectors with quantization. Max dims was not checked.
- **Keyword search:** Yes. BM25 full-text on text payload fields that have a full-text index. Sparse vectors (e.g. SPLADE) also work.
- **Pause / expiry:** Free forever. A cluster left unused is suspended after 1 week and deleted after 4 weeks of inactivity if not reactivated. The daily crawler plus queries should keep it active.
- **Verifier corrections:**
  - BM25 on a payload full-text index is brand new. It arrived in Qdrant 1.20, released 2026-10-22, about 2 weeks ago. It must be turned on per index with `scoring: true`; by default a full-text index only filters. Before 1.20, BM25 needed sparse vectors (the Qdrant/bm25 model). The cluster must run 1.20, and on the free tier version upgrades cause downtime. I could not confirm that new free clusters start on 1.20.
  - The claim says to use the uint8 datatype. That won't work for gte-small: Qdrant's uint8 type only takes values from 0 to 255, so normalized float embeddings would have to be re-scaled first. Use float16, or float32 with scalar (int8) quantization.
  - Max dense dimension is 65,536, so 384 is fine. The claim left this unchecked.
  - RAM is tighter than the claim suggests once indexes are counted. Qdrant's sizing formulas are: dense = n*dim*bytes, HNSW = n*m*2*4*1.2, payload index ~ indexed bytes*2, pinned in RAM by default. For 400k rows: float16 vectors ~307 MB + HNSW (m=16) ~61 MB + a pinned full-text index on name+description (~500 B per row) ~400 MB, plus BM25 scoring overhead (size not documented), comes to roughly 0.8 GB of the 1 GB. Payload defaults to the cold (disk) tier: ~840 MB on the 4 GB disk, which is fine. Workable, but you'll likely need int8 quantization and the full-text index moved to the cached tier.
  - The free tier is described as 'for prototyping and testing' (create-cluster docs). It has no dedicated resources, no backups or disaster recovery, manual API-only snapshots, upgrades with downtime, and limited regions. It is not a ToS commercial-use ban, but there is no SLA.
  - The general ToS lets Qdrant 'terminate or suspend Your access immediately ... for any reason whatsoever'. There is no free-tier-specific clause.
  - The docs don't define what counts as activity for the 1-week suspension. A third-party guide (June 2026) says reads and writes both count, but Qdrant doesn't say so. Treat the daily crawler upsert as the keep-alive, and keep Supabase or another source as the system of record so a deletion can be rebuilt.
- **Blockers:**
  - Keyword plus dense RRF in one query needs Qdrant 1.20 or later (released 2026-10-22), with a full-text index created with scoring:true. Check that the free cluster offers 1.20. Otherwise the fallback is client-side BM25 sparse vectors (Qdrant/bm25).
  - The 1 GB RAM must hold the vectors, the HNSW graph and the pinned payload/full-text indexes. At 400k rows this needs float16 or int8 quantization, plus a cached-tier full-text index, to stay under about 1 GB.
  - Inactivity deletion after 4 weeks with no backups on the free tier. Keep a rebuildable source of truth and run the daily crawler or a keep-alive.
  - Not Postgres: no SQL, plpgsql RPCs or RLS. Access is only by API key, which is acceptable because all access is server-side.
- **Migration:** Medium. Port the hybrid_search plpgsql RPC to a Query API call from TypeScript: a dense prefetch, a text (BM25) prefetch and query {rrf:{}}. Move the filters (categories text[], kind, etc.) to payload indexes. Add a Qdrant upsert step to the crawler, which already builds gte-small vectors locally. Swap Supabase reads in the Vercel routes for @qdrant/js-client-rest using a server-only API key. Lowest-risk shape: keep Supabase (slimmed, no embeddings) as the metadata and source-of-truth store, and put embeddings plus search fields (name, slug, description, categories) in Qdrant as payload. A full move off Postgres is possible because the payload can carry all metadata (disk-tier payload ~840 MB at 400k rows), but it loses SQL migrations, RLS and joins.

A deleted free cluster cannot be restored from the recycle bin. The separate $100 / 30-day trial credits are not the free plan.
- **Verifier corrections:**
  - BM25 full-text search on Free is CONFIRMED, not unknown. The zilliz.com/pricing comparison table shows checkmarks in all 5 plan columns (Free, Serverless, Dedicated Standard/Enterprise/Business Critical) for both 'Hybrid search' and 'Full text search', checked in the raw HTML of the page on 2026-11-08.

They do NOT explicitly say resume is manual for Free; the manual-resume wording is from the Dedicated manage-cluster page. An older Zilliz blog said 14 days. With daily crawler writes and hundreds of queries/day, the inactivity rule should never trigger for this workload anyway.
  - Storage overflow is not graceful: the FAQ says inserting past capacity returns a disk quota error and recommends upgrading. The '~1M 768-dim vectors' figure is described as depending on schema. The claimed docs warning about VarChar/JSON memory overhead was not found on the pages fetched today (unverified).

Estimate for this workload, my own arithmetic: ~10k hybrid searches/month at ~10-20 vCU each = 0.1-0.2M. Upserting a few thousand changed rows per day (~2.2 KB each with an fp32 vector) = ~0.2-0.25M/month. The one-time initial load of 145k-400k rows = ~0.1-0.22M. Total is well under 2.5M. But if the crawler re-upserts all 145k+ rows every day, that is ~0.2M+ vCU/day, about 6-7M/month, which exceeds the quota. Upserts must be limited to changed rows.

  - Behaviour when the monthly vCU quota is exhausted is undocumented. Daily full re-upserts of the catalog would exceed 2.5M vCU/month; upserts must be limited to changed rows (delta writes).
  - No snapshots/backups on Free and no recycle-bin restore. The collection must be rebuildable from Postgres or the crawler.
  - BM25 uses the Milvus analyzer (standard by default), not Postgres tsvector, so keyword ranking will differ from the current FTS. The eval set should be re-run.

### Neon (Free)

- **Vector:** pgvector with vector (2,000-dim HNSW), halfvec (4,000-dim HNSW/IVFFlat), bit, sparsevec; example shows 0.8.0.
- **Keyword search:** Native Postgres tsvector/GIN.
- **Pause / expiry:** Permanent, not a trial. Compute suspends after 5 min idle (cannot disable), so expect cold starts. Hitting CU-hour or egress limits suspends compute until next billing period. Over storage, writes fail. No data deleted.
- **Verifier corrections:**
  - The 1 GB per project limit is new. Neon's changelog dated 2026-10-02 says it was raised from 0.5 GB, and existing projects get it automatically. Older blogs and third-party sites that say 0.5 GB are out of date, and a limit that just changed could change again.
  - Neon does not say exactly what the Free 1 GB storage cap measures. The plans page says storage is 'your data size' and that root branches are billed on logical data size. The glossary says logical data size includes tables and indexes. That the Free cap uses the same measure is an inference: the plans page and the FAQ (updated 2026-11-03) only state the 1 GB number. Instant-restore history has its own separate cap (6 h, up to 1 GB of changes). Logical size is the on-disk database size, so dead tuples and HNSW bloat left by the daily upserts also count. Plan on regular VACUUM.
  - The compute risk is understated. Saying the workload 'could approach 100 CU-h' is too mild; it can go over. Compute suspends only after 5 minutes with no queries. With 300 queries a day spread evenly, the gap between queries averages 4.8 minutes, so the compute never sleeps: 720 h x 0.25 CU = 180 CU-h a month, against an allowance of 100. Even 150 queries a day spread evenly comes to about 94 CU-h. When CU-hours run out, compute is suspended for the rest of the billing period: existing connections drop and new ones are refused, so the site goes down. Autoscaling up to 2 CU uses the allowance up to 8 times faster. Mitigation: cap the compute at 0.25 CU (min = max), which gives 400 running hours a month. Queries that come in human bursts help.
  - Cold starts are short. Neon says a suspended compute wakes 'within a few hundred milliseconds', not seconds.
  - pgvector is 0.8.0 on Postgres 16 and 17, and 0.8.6 on Postgres 18 (from the extensions page). The 0.8.0 shown in the example is not the latest for every Postgres version.
  - Full-text search is native tsvector/GIN only. pg_search (BM25) is listed as 'Unavailable' on every Postgres version. That is fine for the current RRF hybrid, which uses ts_rank.
  - maintenance_work_mem is set from the minimum compute size. At 0.25 CU (1 GB RAM) the default is about 64 MB, so a 145k-400k row halfvec HNSW build will spill and be slow. You can SET it per session, up to about 60% of RAM (about 600 MB at 0.25 CU, more if the build runs at 2 CU, which costs more CU-hours).
  - Moving off Supabase is more than 'roles anon/authenticated need creating'. The crawler and app call supabase-js .rpc()/.from() through PostgREST (crawler/db.ts, crawler/embed.ts). Those calls must be rewritten for a Postgres driver such as @neondatabase/serverless, or moved to Neon's Data API, which needs JWT auth and has no Supabase service-role equivalent documented. The query-time `embed` Edge Function (gte-small) is a Supabase feature and would also have to move, for example to Transformers.js in a Vercel Node function.
  - Free-tier facts that are confirmed: permanent with no trial, no card needed, projects are not paused or deleted for inactivity, data is never deleted when a limit is hit, 100 projects, 10 branches per project, 1 manual snapshot, 1-day monitoring retention, 5 GB egress per project per month (shared with Object Storage and Functions), 20 GB account-wide cap enforced separately, community support only, no SLA.
- **Blockers:**
  - 1 GB per-project storage cap. At 250k rows the estimate is about 0.9 GB with heap, halfvec, HNSW and GIN: borderline. At 400k rows it is about 1.3 GB or more, over the cap. Upsert bloat counts too. Without trimming (for example dropping raw jsonb or shrinking descriptions), writes fail within the year.
  - 100 CU-hours per project per month, with scale-to-zero only after 5 minutes idle (cannot be disabled). A few hundred queries a day spread across the day keep the compute awake and use about 180 CU-h a month at 0.25 CU. Compute is then suspended until the next billing period and the app is down. You must pin the compute at 0.25 CU and watch usage; there are no spending notifications or metrics export on Free, and only 1 day of monitoring.
  - Splitting metadata and embeddings across two Free projects keeps each under 1 GB, but loses the single-SQL hybrid RRF query: you would fuse results in application code. Each project gets its own 100 CU-h, though.
  - Not a hard blocker: query-time embedding currently runs in a Supabase Edge Function and must move off Supabase.
- **Migration:** Moderate. The schema, plpgsql RPCs (hybrid_search, upsert_capabilities, set_embeddings), the halfvec HNSW index, the tsvector GIN index and RLS all port as standard Postgres via pg_dump/pg_restore or by replaying supabase/migrations. Supabase-only pieces need work: anon/authenticated roles and grants, the supabase-js client calls in crawler/db.ts and crawler/embed.ts and the app's server routes (switch to the @neondatabase/serverless or postgres driver and call the functions with SQL), and the `embed` Edge Function (move gte-small query embedding into a Vercel Node function with Transformers.js, keeping the same model so vectors stay identical). Expect slow HNSW builds unless you raise maintenance_work_mem per session. Roughly 1-2 days of work.

The FAQ says credits 'in most cases' do not expire, but after they are spent, usage is billed: $2.50/GiB written, $0.33/GiB-month storage, $0.0075/TiB queried. Sources: https://www.trychroma.com/pricing and https://docs.trychroma.com/cloud/pricing (whether the credit is one-time or monthly is ambiguous on the official pages).
- **LanceDB Cloud:** The official pricing page (https://lancedb.com/pricing/) shows no free tier or credits. A third-party report (usagepricing.com, 2026-08-28) says the self-serve Cloud tier was folded into Enterprise and the cloud docs now 404. An earlier offer was $100 in one-time credits. A current free tier could not be confirmed (low confidence).
- **turbopuffer:** No free tier. The launch plan has a $16/month minimum (scale $256, enterprise from $4,096). Source: https://turbopuffer.com/pricing
- **Google AlloyDB for PostgreSQL:** No always-free tier; only a 30-day free trial cluster (8 vCPU, 1 TB). Source: https://docs.cloud.google.com/free/docs/free-cloud-features
- **Google Cloud SQL:** No always-free tier; only a 30-day free trial instance. Source: https://docs.cloud.google.com/free/docs/free-cloud-features
- **Google Cloud $300 Free Trial:** Credits valid for 90 days only. Source: https://docs.cloud.google.com/free/docs/free-cloud-features
- **AWS RDS / Aurora PostgreSQL:** Covered only by Free-plan credits (up to $200, 6 months; the account closes after 6 months). No always-free allowance shown. Source: https://aws.amazon.com/free/
- **AWS S3 Vectors:** No always-free storage, PUT or query allowance; only the first 512 KB returned per query is free. Source: https://aws.amazon.com/s3/pricing/
- **AWS OpenSearch Service:** Not listed as always-free on https://aws.amazon.com/free/; would rely on 6-month credits (limits page not checked).
- **Azure free account extras (incl. Azure Database for PostgreSQL, extra Cosmos 400 RU/s + 25 GB):** 12-month Azure free account benefits, not lifetime. Source: https://learn.microsoft.com/en-us/azure/cosmos-db/free-tier (Azure Database for PostgreSQL's own free-offer page not loaded)
- **Oracle Cloud 30-day trial credits:** Time-limited trial; only the Always Free resources above are counted. Source: https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm
- **IBM Cloud USD 200 database credit:** Promotional credit, not a lasting free tier. Source: https://www.ibm.com/products/cloud/free/databases
- **Supabase Vector Buckets (S3-backed vector storage, s3_vectors schema):** Not available on Free. The launch post (2025-12-01) says Public Alpha for 'Pro projects and above'. It is free during the alpha under fair use, but that is time-limited and needs Pro ($25/mo). The current docs still carry the alpha warning, and no page states Free availability or GA pricing. Limits in the alpha: 10 buckets/project, 10 indexes/bucket, 4096 dims, up to 50M vectors/index, topK max 10,000, 100 results/response. It also has no full-text search, so hybrid would need app-side fusion. Sources: https://supabase.com/blog/vector-buckets, https://supabase.com/docs/guides/storage/vector/limits, https://supabase.com/docs/guides/storage/vector/introduction
- **Supabase Analytics Buckets (Iceberg):** Not relevant: analytics/Iceberg storage, not ANN or FTS serving. Free-plan availability was not confirmed on the pricing page (no row for it). Source: https://supabase.com/docs/guides/storage/analytics/pricing (not loaded; listed only in search results). Low confidence.
